## 当前结论

串口目前正常。Dock 的 USB-JTAG Type-C 在本机提供 COM13，已按 115200、8N1、无流控打开，并用缺少数字的 `F\r` 指令收到 `ERR\r\n`。这条指令在 Flash 基线中只触发错误回复，不改变音高或音量。JTAG 只读操作又确认 `ID Code=0x0000081B`、`User Code=0x000059D1`，板上确实还在运行之前的 Flash 测试版本。不能把 GitHub 四声部代码已经存在理解成板上也已运行四声部版本。

主分支的四声部结构适合作为扩展基础，当前没有达到完整的可演奏交付状态。独立回归确认了 ADSR 松键不释放的缺陷，原有三个测试台没有覆盖它。应先修复停音和重新触发，再把触摸、压力与标准 I2S 接成完整链路。32 声部在这块板上有实现空间，建议采用四条并行流水线，每条时分处理八个独立声部；无需更换主控或引入 DDR3 查波表。

团队已确认可集中投入 90–120 小时，并表示还能适当增加。建议用约 110 小时完成 32 声部、至少两种音色、三维输入、标准 I2S、延迟效果与 LED 指引，再将新增时间用于抗混叠、合唱、OLED 波形显示和稳定性证据。后文给的是实现预算与验收计划，新增功能尚未编码或在板上验证。

## 2. 串口原因与硬件设置

Windows 当前枚举到了同一 USB 复合设备的两条接口：`MI_00` 为调试通道，`MI_01` 的串口子设备为 COM13，驱动为 FTDI `2.12.28.0`、服务 `FTSER2K`、状态 OK。用户确认电脑 USB 线直接插入 Dock 的 USB-JTAG Type-C，LED2 闪烁且耳机有声音。实测 COM13 能打开且收到协议回复，USB、驱动、板载桥、FPGA UART 接线与接收/发送通路目前均可工作。

旧记录中的“无法识别”不是当前仍存在的硬件故障。本次发现 `Get-CimInstance Win32_SerialPort` 只返回蓝牙端口，漏掉 COM13；`Get-PnpDevice` 和 `[System.IO.Ports.SerialPort]::GetPortNames()` 都能列出它。只依赖前一个 WMI 类的工具确实可能漏报。项目现有 `tools/serial_console/serial_console.ps1` 已使用 .NET 枚举，因此不能把 WMI 漏报认定为该控制台的确定根因。它的下拉框可编辑，可刷新后直接输入 COM13。此前发生问题的具体软件、现场端口状态和失败日志没有提供，历史原因仍只能缩小范围，不能事后确定。

实际使用时选择 COM13、115200、8N1、无硬件流控，并发送 CR 或 LF。当前 Flash 接受 `F440` 一类整数频率命令，主分支四声部接受 `N69` 等 MIDI 音符命令。旧控制台的快捷按钮匹配 Flash 单声部协议；换到四声部固件后应更新它的快捷命令。设备没有主动打印开机文字，打开窗口后空白本身不能说明未识别。若以后出现占用错误，先关闭其他串口工具再打开，端口号也可能随 USB 插口变化。

已经视觉核对 Dock3714 原理图。FPGA TX 为 M11，RX 为 T13，Bank2 为 3.3 V。旧规划里的 N6/N7 实际是 RGB LCD 网络，应停用那段接线说明。BL702 的 SW1 是固件升级 Boot 按键，J16 的 2–3 脚短接会关断 BL702；正常调试保持默认运行条件。自定义 USB Type-C 连接的是 USB3317，不能自然当作调试串口使用。

3714 相比 3713 交换了 SW0 与 KEY4 的引脚：SW0 现为 C7 的 1.5 V 用户输入，KEY4/S4 为 B10 重配置网络。因此旧 Wiki 中“拨码第一位使能核心板”的说明不能未经版本核对直接套用。本次已有正常发声、串口往返和器件读回，不需要改变拨码、Boot 状态或桥接固件。

JTAG 查询另有工具选择问题：默认命令误选 GWU2X 后虽然进程返回 0，文字却报告打开失败。根据扫描给出的 USB Debugger A 通道与位置，明确传入通道 0、位置 9025 后，实际使用 FT2CH 并成功读回器件。位置号会随连接变化；“退出码 0”不能单独证明编程器操作成功，应检查 Finished 和器件返回值。

## 3. 算法与资源复查

### 已经复现的功能缺陷

`adsr.v` 的上层条件是 `!gate && state != ST_IDLE`。松键后它在每个采样节拍不断把状态设为 RELEASE，后面的 RELEASE 减法始终得不到执行。独立测试台先把包络推进到稳定电平，再松键并等待 2000 个采样节拍，结果为 `env=45875、idle=0、state=4`，最终由 `$fatal` 返回失败。这会使声音不停止、空闲声部不回收，并让旧音持续占用混音空间。建议只在进入 RELEASE 的边界改变状态，让 RELEASE 分支持续递减；测试同时覆盖 ATTACK/DECAY/SUSTAIN 中松键、释放归零及再次起音。

Python `render_preview.py` 的 `_adsr()` 没有同样的上层条件，释放可以继续递减，且它在 ATTACK/DECAY 中也没有按 RTL 行为处理提前松键。这意味着当前试听文件不能作为 RTL 等价证据，历史音量与气口结论需要在修复后重新比对。建议从 RTL 捕获逐采样输出，再由独立数学模型核验频率、包络边界和削波，不仅试听 Python 生成的 WAV。

### 还需覆盖的架构问题

`voice_alloc` 在声部窃取或重用时只更新 note、velocity，并把 gate 置 1；没有独立 retrigger 事件。若所选声部的 gate 原本已经为 1，或包络尚在 RELEASE，新的音符不一定重新进入 ATTACK。需要定义重新触发与短淡出规则，补“满复音再按一个键”“快速重复同音”和“释放期间重按”测试。此处是代码审阅结论，本次没有额外实现或声学验证。

顶层播放序列始终启用，UART 与它共享分配器，真实键盘接入后会与演示抢声部。应设置独立的演奏、曲目指引、自动演示和多振荡器测试模式。S3 对声音模块使用 `rst`，分配器等部分使用 `por`，软件复位语义也要统一；目前按复位后旧 gate 仍可能保留。事件 FIFO 的 DEPTH 参数与固定 AW=4 不一致，full 没有接到生产者、没有丢事件计数；32 声部和多个输入同时接入前需要真正的握手、溢出计数与 Note Off/Panic 优先处理。16 位 age 的普通最小值比较在回绕后不再可靠，应做模差比较或明确重排年龄。

当前混音 `VOLUME_SHIFT=1` 只把四路和除以二，四个满幅同相音仍会削波。测试曲未削波不能证明所有复音组合均安全。32 路 16 位声音求和至少需要 21 位有符号宽度，建议混音、反馈和后续滤波保留 24 位及必要保护位，在最终输出前统一增益和饱和，同时提供 clip 计数。24 位 I2S 槽不意味着 16 位波表自动获得了 24 位有效精度。

`(1,4,6,4,1)/16` FIR 是明显的低通：幅频为 `|cos(πf/Fs)|^4`，当前 Fs 下 10 kHz 约衰减 8.5 dB。对正弦调试可以接受，对明亮乐器音色会削弱高频。应在正式链路提供旁路或设计有明确带宽的滤波，靠按音区选择带限波表控制谐波混叠。线性插值减少查表误差，不能消除高次谐波超过奈奎斯特频率产生的混叠。

目前 DDS 写成 `$readmemh` 推断数组，实际重建确实映射成四块 BSRAM pROM，没有变成大 LUT ROM。为符合项目既定约束并固定同步读延迟，扩展版应使用 Gowin ROM IP 或原语，同时配仿真模型。音符增量中的 `/12`、`%12` 在四路上可综合，但复制到 32 路没有必要；可在音符事件接收时通过一份频率 ROM 算出并保存 phase_inc。

## 4. 十月底目标与资源配置

[高云 2026 官方赛题](https://www.gowinsemi.com.cn/university/match2026) 的基础指标是至少二维交互、至少四复音、HDL 实时合成、ADSR/实时变调/混音与总延迟不超过 10 ms。扩展关注至少 32 复音或等效并行单元、三维控制、两音色、硬件效果及更低延迟。评分使用可闻独立振荡器数量与实际输出采样率的乘积，现场要展示对应谱峰。官方写的是 I2S 至 DAC，并没有限定 PCM5102A；选用它和两个 512 点表是本项目的方案约束。

建议正式版本用 32 个独立相位、频率字与包络状态，48 kHz 实际输出，吞吐量目标为 `32×48000=1536000` 振荡器样本/秒。12 个触摸键负责选音与和弦，FSR 控制力度/持续表情，ADC CH1 上的线性电位器提供独立连续弯音。参数菜单编码器不应直接替代第三个演奏维度的验证。全路径继续使用 HDL，BL702 只作 USB-JTAG/UART 桥，不参与音频计算。

采用四条并行合成流水线，每条保存八个声部的独立上下文并时分运算。每条共享一组两音色 ROM 及插值、包络、力度乘法，最终汇总混音，接公共效果器和 I2S。声部之间共享算术单元不改变其独立振荡器属性，验收仍要证明 32 个声部同时可闻，频率、相位与包络互不覆盖。

单一 12.288 MHz 域在 48 kHz 下有 256 个时钟/帧。每声部预算 16 个时钟，四条流水线各处理八个声部，共 128 个并行调度时钟；再给混音、效果、控制和安全间隔预留约 80 个时钟，设计预算为 208/256。这个时序分配是实施目标，必须用 cycle counter 和断言证明每帧截止时间，不能仅按平均乘法吞吐量说足够。I2S 序列器持续输出上一帧的稳定结果，处理延迟固定为整数帧。

12.288 MHz 产生 3.072 MHz BCK、48 kHz LRCK，64 BCK/帧，可传 24 位数据及槽填充。优先保留最低设计文档的单音频时钟域；UART 分频、I2C/SPI 分频、频率字、曲目时值和 ADSR 步进都必须随时钟/采样率调整。外部晶振必须接已经核实可用的 3.3 V GCLK，而不是随意接普通 PMOD。本次视觉追踪已找到 `J14 第10脚 → MIC_DAT3 → T7/GCLKT_3`，位于 Bank3；邻近第9脚为 `MIC_DAT2 → R8/GCLKT_3`。优先选择 J14-10/T7，在未接麦克风阵列、排针和 FPC 上均无其他驱动的前提下，先用万用表确认连通与默认3.3V电压，再接短线晶振、串阻与去耦。此前“PMOD 是否引出 GCLK”已有明确图纸依据，实物连通、电压、振荡器波形与 PRIMARY 路由尚未验证。M11 已用于 UART，H11 已由板载晶振驱动，不可把另一晶振直接并上去。若实物条件不允许这一路，可评估其他 GCLK 或外部参考 PLL，届时重新出资源与时序预算。

新增外设可优先利用空闲 LCD 排针，候选如下。这是接线提案，未应用到 CST。只有未连接 RGB LCD 等共用外设、确认3.3V域后才实施；J5/J6/J14方向按丝印和原理图编号识别，不能靠插头朝向猜测。

直接复制当前四声部实现到 32 路，每路三个乘法器就会需要 96 个 18×18，超过 48 个。若改成每声部两个 1024 点表，64 块 BSRAM 又超过 46 块。四流水线共享 ROM 和乘法器正是本次扩展的主要资源优化。DDR3 可留给日后长延迟、音频回传缓冲或大画面，本月底不放进逐样本查表路径。

除硬件演奏链路外，优先添加可旁路延迟、声部/削波状态、曲目 LED 指引和压力/弯音显示。增加工时后，先做带限波表与音质比对，再做共享缓冲的合唱与 OLED 波形。大 FFT、复杂长混响、HDMI 全屏、USB-MIDI 主机、手机 App 和 DDR3 控制器目前没有提供足以抵消联调成本的验收收益，可在上述主目标全部实测通过后再选。96 kHz 只有真实输出且全部振荡器保持活跃才增加吞吐量，它会压缩每帧预算，应放到末期单独评估。

新增工时建议另安排约 12 小时做四音区带限波表、约 6 小时做合唱、约 8 小时做 OLED 波形与证据补充，具体增加量仍由团队决定。两人可以分别承担 RTL/仿真和硬件/测量，再在每个阶段共同联调。表中的小时是团队总量，不能把两人的时间重复相加。采购到货、可借仪器和 GCLK 接线是计划前提，10/14 前应落实。

10/18 必须先有符合基础要求的完整四声部链路。10/22 若 32 声部调度没有通过仿真和 PnR，保留 8/16 声部稳定演奏配置，暂停 OLED/合唱，优先把 32 声部测试和声音一致性问题关掉。到 10/27 后不再引入新协议、DDR3、无线或大显示架构。截止日前增加功能的标准是它已通过仿真、资源与时序，以及板上验收，不能以“能综合”代替完成。

触摸路径应使用 MPR121 IRQ 与 400 kHz I2C，约 0.12 ms 的状态读取预算。不要复用板上按键 38.8 ms 去抖。传感器内部 ESI、SFI、触摸阈值与 debounce 共同决定响应速度，设置 1 ms ESI 并不证明总延迟是 1 ms。压力与弯音建议 2 kHz 更新、SPI 先用不超过 1 MHz，触发快路径采用短滤波；避免让旧方案的慢 IIR 把所有控制边沿拖到 5 ms 以上。

延迟至少做 200 次不同相位触发，分别记录物理动作参考到模拟输出、IRQ 到事件接收、事件到 I2S 更新的最小/最大值和峰峰抖动。只测 IRQ 到 I2S 会漏掉传感器检测和 DAC 滤波。正式验收先确保最坏值不超过 10 ms，再以最坏值不超过 5 ms 为扩展目标；“固定音频帧调度”不等于异步物理输入真的零抖动，数据应如实报告。

32 声部测试使用分离的音符频率并核对实际活跃数，保留 FFT 峰值及每声部相位/包络状态。不能用一个包含 32 个谐波的波表宣称 32 振荡器。另测四个同相满幅音、32 个同相音、最大反馈、Note Off 全释放、FIFO 满、重复同音、非法串口输入及压力断线。所有生产 Verilog 改动继续先通过自检 RTL 仿真门禁，再做硬件烧录。

官方目前写明作品提交为 2026-11-04 18:00，10/31 是本团队冻结目标，可留下几天材料缓冲。推荐板卡名单未列 Primer20K；本地规划称允许自备第三方高云板，本次没有取得该条当前有效的官方确认，因此仍需团队向主办方确认并保存依据，不把它当作已核实参赛资格。
