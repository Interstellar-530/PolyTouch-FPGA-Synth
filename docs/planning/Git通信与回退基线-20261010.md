# Git 通信检查与版本回退基线

日期：2026-10-10

本文记录本轮对本机与 GitHub 仓库之间通信情况的检查结果，并给出后续调试代码时回退前序版本的具体办法。目的只有一个：让每次改代码之前都有一个可退回的确定状态。

## 一、结论

本机与 GitHub 仓库的读写通道都正常。经本机代理访问，`git fetch` 能拉到远端引用，`git push` 能把本地提交和标签写回远端，回读 `git ls-remote` 得到的结果与本地记录逐字一致。仓库地址是 `https://github.com/Interstellar-530/PolyTouch-FPGA-Synth.git`，工作分支是 `main`。

已经为当前已知可用的固件状态建立了一个回退标签 `v0.4-20261010`，指向提交 `39a0732`，并已推送到远端。以后任何调试只要觉得改坏了，都可以从这个标签恢复。

## 二、通信检查过程与证据

检查分三步，全部保留原始输出要点。

第一步，确认本地工作区干净。`git status` 返回 `On branch main`、`Your branch is up to date with 'origin/main'`、`nothing to commit, working tree clean`，说明检查前没有未提交的改动。

第二步，拉取远端引用。命令 `git fetch origin --prune` 返回 `From https://github.com/Interstellar-530/PolyTouch-FPGA-Synth`，并报告远端存在分支 `fix/m2-build-issues`。这条命令能完成，说明读取方向的网络和认证都通。

第三步，回读远端引用。命令 `git ls-remote origin` 返回 `refs/heads/main` 指向 `b05bc34`，这就是本轮新增规划文档后的提交；同时返回 `refs/tags/v0.4-20261010`。本地 `git rev-parse HEAD` 与远端 main 一致。

推送时的输出是 `39a0732..b05bc34 main -> main` 和 `[new tag] v0.4-20261010`，两条都返回退出码 0。

需要记录的一个环境事实：命令在沙箱内执行时不能访问外网，直接跑 `git fetch` 会报 `schannel: AcquireCredentialsHandle failed`。本机配置了 GitHub 专用代理 `http.https://github.com.proxy=http://127.0.0.1:7897`，经提权（绕过沙箱联网限制）执行后一切正常。所以以后联网类 Git 命令都要走提权，这属于预期行为，不是故障。

## 四、回退基线

软件基线是标签 `v0.4-20261010`，对应提交 `39a0732`，也就是"UART 引脚更正为 M11/T13、SRAM 与外部 Flash 均已写入"的那一版。它是本轮确认过能正常发声、能读器件码的状态。

硬件基线是当前写在板载外部 SPI Flash 里的码流。SHA256 为 `80089e293129be7f77c7ee32c630690f769eb4417e579392f83182b4b8e9357a`，User Code 为 `0x000059D1`。因为设计已经在 Flash 里，掉电或按 S4 重配置后都会自动加载回这一版，所以只要 Flash 不重写，板子随时能回到这个发声正常的基线。

今天的工作分成多次提交，粒度较细，必要时可以回退到其中任意一个。几个关键节点是 `b05bc34`（本轮规划文档）、`39a0732`（UART 引脚更正）、`5899a70`（串口控制台指向 USB-JTAG）、`0726891`（FIR 系数修正）、`b9f558f`（PT8211 字对齐修正）。

## 五、回退操作手册

下面几条命令按由轻到重的顺序排，日常调试建议只用前两条。

查看历史与差异用 `git log --oneline -20` 和 `git show <提交号>`，先看清楚再动手。

临时回到某个旧版本看代码，用 `git switch --detach <标签或提交号>` 进入游离状态，看完用 `git switch main` 回到主线。这种方式不动任何历史，最安全。

想在旧版本基础上重新开发，用 `git switch -c recover/v0.4 v0.4-20261010` 新建一条恢复分支，主线 `main` 保持不动，试好了再决定是否合并。

想撤销某一次已经提交的改动但保留后面的历史，用 `git revert <提交号>`，它会生成一个反向提交，适合已经推送过的内容。

只有在明确要丢弃本机改动、彻底回到基线时才用 `git reset --hard v0.4-20261010`。这条命令会删掉工作区里所有未提交的改动，执行前必须先用 `git status` 确认没有需要保留的东西，属于高危操作。

如果误删了提交或分支，用 `git reflog` 找到操作前的提交号再恢复。当前仓库的 reflog 记录完整，本轮检查时有 16 条记录。

推送到远端的标签不会自动跟着分支回退，回退后如果远端也想要旧的提交，需要单独 `git push origin <分支>` 或重新打标签。

## 六、调试期间的版本纪律

每开始一项新功能之前，先确认 `git status` 干净，必要时为新功能单独开一条分支，例如 `git switch -c feat/poly4`。每完成一个能通过听感或报告验证的小步骤就提交一次，提交信息写清楚改了什么、依据是什么，这样任何一步出问题都能精确定位到对应提交。

对硬件版本也要留档。每次重新生成码流后，把 `.fs` 文件的 SHA256 和器件读回的 User Code 记到调试日志里。将来某次改动导致听感变差时，可以先用旧码流写回 SRAM 做对照，一行命令就能判断问题在代码还是在板级。

## 七、环境遗留项

`.git` 目录的属主问题本轮之前已经修复，不带 `-c safe.directory` 也能正常执行 git 命令。工作区根目录还留有一个 `.git_owner_bak2_20261010` 目录，是上一次修复属主时留下的重复副本，大约 8.9 MB，里面的对象文件属主仍是沙箱账户，普通权限删不掉，已经写进 `.git/info/exclude` 以免影响 `git status`。清理它需要在管理员 PowerShell 里执行：

```powershell
takeown /f "E:\Working Space\FPGA\.git_owner_bak2_20261010" /r /d y
Remove-Item -LiteralPath "E:\Working Space\FPGA\.git_owner_bak2_20261010" -Recurse -Force
```

这条命令只删那一个备份目录，位于工作区内且路径明确，不影响仓库和源码。
