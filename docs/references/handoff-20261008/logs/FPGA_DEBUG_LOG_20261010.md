## 本轮反馈

用户已经接上耳机，能听到音调，并报告两个问题：播放时背景噪声很大；不切换按键时声音会周期性通断，像警报一样嗡鸣。

## 问题一：警报式嗡鸣

根因在 `source/rtl/top.v`。上一版为了让包络可以被观察到，用 `gate_cnt` 每 0.25 秒把 ADSR 的门控拉低再拉高，于是输出变成 2 Hz 的断续音。修改方式是删掉整个 `gate_cnt` 计数器和 `assign gate = (gate_cnt < 11718)`，改成 `assign gate = ~rst`。复位释放后门控恒为高，包络走完起音和衰减后停在 70% 的延音电平并一直保持，按键只切换 DDS 频率控制字，不再周期性静音。

## 问题二：背景噪声

第一嫌疑是 PT8211 的字对齐。上一版 `pt8211_tx.v` 用 `bit_cnt` 在 15 和 31 翻转 WS，WS 边沿正好落在字的最低位上。PT8211 是右对齐的 Japanese 格式，期望的 WS 位置比这个早一个位。错位之后 DAC 重组字时会用到错误的符号位，听感就是在音调上叠加很重的失真。

修改后按 Sipeed/Gowin 官方 `TangPrimer-20K-example/PT8211/src/pt8211_drive.v` 的结构组织：帧计数 `b_cnt` 走 0..31，`b_cnt` 为 0 和 16 时请求新字，请求延迟一个 BCK 后装载，再下一个 BCK 输出最高位；WS 在 `b_cnt` 3 拉低、19 拉高。官方例程在 BCK 上升沿更新寄存器和 DAC 在同一个沿采样，本设计改成在 BCK 下降沿更新，DAC 仍然在上升沿采样，位流序列不变但建立时间从几乎为零增加到约半个 BCK 周期。

## 验证证据

用 Python 对官方驱动和新模块分别做了寄存器级仿真，把 DAC 在 BCK 上升沿实际采到的 (WS, DIN) 序列逐点比较，两段序列完全相同。仿真脚本放在 `tmp/verify/model.py`，任务结束后删除。

重新构建结果：331 个 LUT/ALU/ROM16、188 个寄存器、1 块 BSRAM、1 个 18×18 乘法器；0 个建立违规端点、0 个保持违规端点；实际 Fmax 113.169 MHz，约束 27 MHz。综合日志没有再出现 `wave_sine.hex` 找不到的警告，正常工程里没有 GAO 核，GAO 占用的资源保持释放状态。

新码流 `artifacts/instrument.fs` 的 SHA256 是 `0612d3383736688423204cd2a04ad2350a110d9c7c7e3f483008a6ddb2faa399`，User Code `0x00009F8A`，已经用 `SRAM Program`（操作 2）写入 SRAM，退出码 0。烧录后不要断电，SRAM 配置会丢失。

## 还没有验证的部分

背景噪声是否真的降到可接受水平只能靠耳朵判断，软件侧的构建和时序只能证明设计本身干净。如果听完仍然有明显噪声，下一步按这个顺序排查：先把 `VOLUME_SHIFT` 临时改成 3 或 4，确认噪声是否跟着信号一起变小；再把波表从 512 点升到 1024 点，重新生成 `wave_sine.hex` 并改查表地址为 `phase[31:22]`；最后才考虑在 `top.v` 里加一阶低通或者怀疑板级模拟通路、耳机、地线。
