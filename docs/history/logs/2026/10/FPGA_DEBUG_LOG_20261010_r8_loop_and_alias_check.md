# 调试日志：循环异常与混叠排查（2026-10-10 修订十五）

## 反馈

现象是曲子播放一小段后开始重复，同时怀疑音频接口波形发生混叠。这两条要分开看，混叠只会改变音色与频谱，不会让曲子提前回头；而提前回头属于音序或时间基准的问题。

## 混叠这一条

把信号链从头算一遍。采样率是 27 MHz 除以 18 得 1.5 MHz 的 BCK，再除以 32 得 46875 Hz，奈奎斯特上限 23.4 kHz。波表是 512 点的一个完整正弦周期，查表时用相位低九位在相邻两项之间做线性插值，把一阶阶梯误差变成二阶，早前实测带内误差是 -94.8 dBFS。混音之后还有一级 (1,4,6,4,1)/16 平滑滤波，它的频响在奈奎斯特处正好是零点。旋律最高音约 700 Hz，是基频为主的正弦，距离奈奎斯特还有三十多倍。整条链上没有采样率变换，也没有把高频折叠回来的环节，所以不存在混叠路径。

## 音序这一条

按当前参数把播放器状态机推了一遍：一圈是 156 个十六分音符单位、41 个旋律音，循环发生在第 0、156、312 个单位处，没有提前回头。歌曲表逐项与 Python 模型比对，零处不一致。UART 接收脚在引脚报告里是带上拉的输入，悬空时保持空闲高电平，不会产生随机字节；S3 复位脚同样有上拉。逻辑层面找不到提前重复的成因。

但综合报告显示歌曲表被推断成了内部存储器，而这类存储器是否把初始化数据完整装好，从报告上看不出来。如果只装了一部分，后面的表项读出来是零，旋律就会在几句之后变成跳着走，听感正好是"播一小段就重复"。

## 处置

先把这一类风险消掉：歌曲表改由 `tools/gen_song_rom.py` 生成 `rtl/audio/song_roms.vh`，里面是三个常量 `case` 函数，`song_player.v` 在模块内 include 使用。表很小（41 项旋律、每组 9 项和弦），用组合逻辑实现既省事又完全不依赖存储器的映射与初始化行为。原来的 `.hex` 文件删掉了。

再给一个能直接测量的出口：N16 指示灯从每秒一闪改成**每走完一圈曲子闪一次**，闪约 110 毫秒。标称循环长度是 1 档 32.5 秒、2 档 65 秒、3 档 97.5 秒、4 档 130 秒。这样只要用秒表量两次闪烁的间隔，就能判断音序和时间基准到底对不对。原本想另外接一个指示灯，但 C13 是 DONE 专用脚、A13 是 READY 专用脚，都不能当用户 IO，所以把心跳功能并进了循环标记。

## 结论与下一步

构建无警告，资源 4576 逻辑单元、786 寄存器、4 块 BSRAM、6 个 DSP，码流 SHA256 `2f4867cf52d2f66603fc54b72517f23a2c0e0467685d384956d5496fdba174ce`，User Code `0x00009525`，已写入 SRAM 并回读确认。

下一步需要一次实测：量 N16 两次闪烁的间隔。若约 65 秒，说明音序与时间基准都对，"重复"来自曲子本身——原谱里"带着兰花草"和"看得花时过"两句旋律完全一样，和弦套 A 的前四句又是 Gm–Cm–Gm–F 重复一次，听上去确实会像回到前面；若明显短于标称值，把实测秒数告诉我，我按比例修正时间基准。
